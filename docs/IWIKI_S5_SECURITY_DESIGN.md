# MuSSE iWiki S5｜受控语音写入安全设计（S5-A）

- 日期：2026-11-04
- 状态：**S5-B 离线核心门禁与纯业务规划器已提交；未接入远端写适配器、未部署、未授权真实写入**
- 基线：`feat/iwiki-s2a-readonly-contract` @ `25a9f64`，PR #24 仍为 Draft、未合并。
- 用户最新方向：不再要求 S4-E 目标/笔记的额外映射与验收，直接推进 S5；**不等于跳过 S5 自身必要的安全测试**。
- 权威交接：`docs/IWIKI_S4D_FINAL_HANDOFF.md`、`docs/STATUS.md`、`docs/TEST_LOG.md`、`docs/DECISIONS.md`（D-018）。

## 1. 不变边界

1. iWiki 始终是任务、目标、笔记的唯一持久化来源。不新建第二任务数据库；本机最多保存短期、非持久的待确认事务状态。
2. 既有 `iwiki` 官方 MCP 和 `musse_iwiki_readonly` 六工具只读服务维持现状；`xiaozhi-client@2.3.0`、其本机日志脱敏补丁、TCP 9999 入站阻止规则、ESP32 固件及 Muse 当前角色提示词不改。
3. 旧 `src/mcp/server.ts` 暴露全部 13 工具，**不得**作为 S5 生产写入口直接连接；`src/mcp/server-readonly.ts` 继续单独保持严格只读。
4. 不在公共仓库、PR、Issue 或日志中存储 Token、真实文档 ID、私人接入信息、任务正文或用户配置。PR #24 保持 Draft。
5. 设计与离线测试可先推进；任何真实文档修改、生产写工具开放、权限升级、Windows/云端/固件配置改动必须分别明确批准。

## 2. 现有源码证据与阻塞

- `src/mcp/tools.ts` 已有业务层写操作：`task_create`、`task_update`、`task_complete`、`task_archive`、`task_restore`、`goal_record_progress`、`note_create`；存在业务逻辑不意味着已安全接入真实远端。
- `src/store/official-iwiki-read.ts` 已通过真实 `read_doc` 返回形状验证，但 `read()` 固定返回 `version: ""`，`write()` 永远抛错。远端条件更新/版本令牌尚无证据。
- `src/store/iwiki-store.ts` 是旧的通用读写适配器，写工具名、参数及成功响应均标为未验证；`writeEnabled` 虽默认关闭，但**不能将它的开关打开就当作 S5 接入**。
- `src/service/task-service.ts` 的任务操作通常采取“读整份 Markdown → 修改 → 写回”路径。若官方 iWiki 未提供原子的版本条件写入（Compare-and-swap），单纯写前重新读取并计算内容哈希不能消除检查与写回之间的并发竞争，可能覆盖用户在 iWiki UI 的编辑。
- 尚未找到可信的独立用户确认通道。模型在 MCP 参数中传入 `confirmed: true`、验证码或所谓用户口述不能独立证明用户真实同意；服务端不可仅信任模型的这一声明。
- 新业务只读 MCP 的写白名单拦截不等于官方 `iwiki` MCP 已在服务端拒写，后续生产写权限需要单独界定。

## 3. S5 总体设计

采用**独立、默认禁用的写网关**，而非扩展原只读服务的公开工具表。建议模块（计划名，尚未创建）：

- `src/write/operation-policy.ts`：精确的操作和字段白名单、日期/ID 校验、禁止删文档和任意正文覆写。
- `src/write/prepare.ts`：仅做读取、对象定位、解析和预览，生成短期事务标识与确认摘要；不得调用远端写工具。
- `src/write/approval.ts`：接入真正由用户触发的可信授权信号，并绑定**事务 ID + 目标 ID + 前后值摘要 + 有效期限**。若客户端不提供可信授权能力，生产提交端默认不可用。
- `src/write/commit.ts`：独立实施确认校验、写前一致性检查、幂等判断、已验证的远端条件提交、写后读回与异常处置。
- `src/write/official-iwiki-write.ts`：仅在拿到真实官方写入工具名称、参数/响应、冲突语义和最小权限证据后实现。不臆造工具契约。
- `src/mcp/server-write.ts`：未来可选的独立入口；除非安全门禁满足且经批准，不能在 Windows 桥接配置中添加，不应在既有只读服务暴露写工具。

### 事务状态机（拟议）

`PROPOSED → AWAITING_TRUSTED_APPROVAL → APPROVED → COMMITTING → VERIFIED`

- 拒绝/过期：`REJECTED` / `EXPIRED`，不写入。
- 并发版本变化：`CONFLICT`，作废该预览，必须重新生成和重新确认。
- 远端超时、响应不明确：`UNCERTAIN`，仅只读核对，不盲目重复提交。
- 任一校验缺失：拒绝，不能向语音端播报“已保存”。

**确认通道必须独立于模型的自述。** 备选包括 Windows 本地受保护的用户批准界面、官方客户端可靠的工具批准机制、或未来独立授权的实体设备确认动作。均应先验证实际可用性；当前不指定或改变固件/桥接实现。单纯“说了确认”而仅由模型传递布尔值属于弱确认，不得描述为服务端强制的人类授权。

### 并发与幂等

- 优先使用官方远端原子条件更新（例如有效的版本令牌）；其契约若不存在或不能证实，**禁止上线会覆盖整篇任务文档的写操作**。本机锁/写前哈希检查仅能降低本机冲突，不能解决其他客户端并发写问题。
- 每次建议操作都要有独立 ID，短期内重复提交只能对应同一意图。禁止因为网络超时盲重试创建/追加；如需跨进程重启去重，应利用 iWiki 记录中的稳定业务 ID 或经验证的远端幂等支持，不能新增持久化数据库。
- 写后以官方 `read_doc` 复核目标记录的关键字段与无关记录；写后读回不等于解决并发，但可避免错误报告成功。
- 审计只能记录非敏感操作类别、状态码、匿名化关联值和阶段，不记录原文、凭证、文档 ID 或整份请求/响应。
- 恢复策略先只读定位结果，再判断是否需要用户介入；不能用未经确认的旧全文自动“回滚”覆盖其他人的修改。

## 4. 首批业务范围

首批**设计**涵盖任务创建、修改、完成、归档、恢复，以及快捷笔记追加。任务状态以任务总表为准，归档不是删除。每个操作必须限制可编辑字段并预览目标及变化。

目标进度记录（`goal_record_progress`）待真实目标文档映射后再接入；不为推进 S5 重新创建 S2-B 三份模拟文档。若笔记映射仍缺失，`note_create` 不得自行猜测或搜索私人文档 ID。

建议分批实施：先建立不可写的准备/确认逻辑与假适配器离线单测；再研究真实远端条件写契约与可信批准能力；最后经独立授权才开启真实受控写入。

## 5. S5-B 离线安全测试最小矩阵（不是重做 S4 验收）

1. 不公开任何写工具时，旧只读六工具及拒写语义保持不变。
2. `prepare` 永不调用写入；目标不存在、候选重复、无 ID 映射、日期格式错误、越权字段全部拒绝。
3. 无可信批准、模型伪造批准、批准对象或摘要不匹配、超时、重复使用令牌全部拒绝。
4. 写前数据变化触发冲突并要求重新确认；无已验证原子条件写契约时禁止整表写回。
5. 同一创建意图重复调用、提交后网络超时、服务重启、写回响应模糊时不盲重试。
6. 成功只有在写后读回验证后才报告；无关任务变化、用户并发编辑及读回不一致均不误报成功。
7. MCP 工具列表、错误消息和日志均无凭证、私有 ID 或整篇数据泄漏。
8. 运行完整仓库常规回归及新增 S5 离线测试，并区分“离线通过”“真实测试环境通过”“生产授权上线”。

## 6. 待证实的实施门槛

- 官方 iWiki 写工具的实际名称、输入 schema、响应 envelope、最小权限及拒写行为。
- 官方是否提供真正的条件更新/原子追加/幂等能力。无法确认时不能宣布安全支持整篇任务表写入。
- 现有小智与 Windows 桥接是否有可信的人类批准信号。无法确认时不得把模型自述当作逐次确认。
- 受控写操作的范围、部署方式和生产开关须在实际接入前另行批准。

本设计已在独立 S5 分支落实为 `src/write/guarded-write.ts` 与 `src/write/plan-write.ts` 及离线测试：模拟端口核心 13/13 通过；纯规划器测试已提交、尚未在完整仓库运行。**没有执行真实 iWiki 写入、没有部署新 MCP、没有开启读写 Token 或写入开关**，不能宣称 S5 已生产可用。

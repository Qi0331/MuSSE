- 用户明确**取消 S2-B 的三篇虚构文档准备、Windows 三文档只读探针验收及逐项语音验收**，不再默认催促运行；原代码、模板和此前测试记录留作历史参考，S2-B 目标与笔记实际只读能力**未验收**，不得记为通过或删除历史证据。

## 2. 下一阶段建议：S4（供用户审查，尚未批准实施）

目标：让 MuSSE 不只读取 iWiki Markdown，还能通过**确定性的业务逻辑**可靠查询任务、日程、长期目标和快捷笔记，并为 S5 的受控写入奠定基础。

- **S4-A 方案审查**：基于现有官方只读 MCP 和 `software/musse-iwiki/` 中现成 `TaskService`、Markdown 解析、`OfficialIwikiReadStore`，评估是否需要在 Windows MCP 路径增加**受限只读业务工具**；明确最小接入点、既有映射、工具可见范围和回滚。优先避免重复造一个服务及破坏当前官方直连。
- **S4-B 任务与日程**：确定性读取任务表，输出今日/未来/逾期/已完成任务。考虑日期时区、表格格式异常和缺失数据。
- **S4-C 长期目标与快捷笔记**：读取关联目标和笔记并可靠计算进度/识别最新记录；不把模型猜测当作精确统计。
- **S4-D 设备语音整合**：以小智自然语言调用只读业务查询，明确回答/工具调用证据边界。
- 用户不希望重新做 S2-B 多篇虚构数据和繁琐验收；仍需保留覆盖关键错误、只读限制和不泄密的最小离线检查。任何修改桥接或运行真实账号前先解释风险并取得用户单独许可。

**新对话第一步**：先给出 S4-A 的可行性分析与两个以上接入路径的比较，尤其确认现有 `xiaozhi-client@2.3.0` 如何暴露只读业务工具。仅在用户审查并明确同意后才开发、修改配置或部署。

## 3. S5 明确后续目标（当前不得实施）

- S5 拟实现任务新增/修改/完成/归档、笔记新增、必要的目标进度操作。
- 写入路径必须考虑白名单、逐次确认、输入校验、作用范围、并发冲突处理、写后读回、失败/重试幂等、审计脱敏和回滚。
- 写入凭证的远端权限尚未独立审计。禁止将「提示词不调用写工具」等同真正写权限防护，禁止擅自发起写请求。
